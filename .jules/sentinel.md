## 2024-05-18 - TOCTOU Vulnerability Mitigation on /dev/urandom Access
**Vulnerability:** Accessing device files like `/dev/urandom` using simple path-based IO (e.g. `withBinaryFile`) lacks validation, potentially allowing malicious actors to replace it with a regular file or named pipe if they have sufficient permissions (a TOCTOU - Time of Check to Time of Use - vulnerability).
**Learning:** In a security-focused medical device environment, all device file accesses must be verified using system calls (`getFdStatus` and `isCharacterDevice`) AFTER opening the file descriptor to prevent TOCTOU substitution attacks.
**Prevention:** Always open the file descriptor first (`openFd`) and then validate its status. When doing one-off reads, use `bracket` with `closeFd` to safely manage the lifecycle of the file descriptor.
## 2024-05-18 - TOCTOU Vulnerability Mitigation on /dev/urandom Access
**Vulnerability:** Accessing device files like `/dev/urandom` using simple path-based IO (e.g. `withBinaryFile`) lacks validation, potentially allowing malicious actors to replace it with a regular file or named pipe if they have sufficient permissions (a TOCTOU - Time of Check to Time of Use - vulnerability).
**Learning:** In a security-focused medical device environment, all device file accesses must be verified using system calls (`getFdStatus` and `isCharacterDevice`) AFTER opening the file descriptor to prevent TOCTOU substitution attacks. Additionally, when using `System.Posix.IO`, `fdToHandle` takes ownership of the file descriptor, so using `closeFd` via a `bracket` pattern will introduce a double-close bug. Using `fdRead` avoids handle conversion entirely but returns a tuple `(ByteString, ByteCount)`.
**Prevention:** Always open the file descriptor first (`openFd`) and then validate its status. When doing one-off reads without Handles, use `bracket` with `closeFd` and read via `System.Posix.IO.ByteString.fdRead`, remembering to unwrap the returned tuple.
